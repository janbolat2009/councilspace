# Департаменты Council Space

Реализация расширяет существующий Next.js / Prisma / NextAuth проект. Авторизация использует Google и email/пароль; Supabase предоставляет PostgreSQL, а не клиентскую Supabase Auth-сессию. Дизайн и существующие задачи, отчёты, начисления, календарь, чат, лидерборд и модерация сохранены.

## Регистрация и доступ

В регистрации доступны семь направлений: интеллектуальное развитие, спорт, волонтёрство, менторство, финансы и External Affairs, масс-медиа, менеджмент. Каталог находится в `src/lib/departments.ts`.

Email-регистрация сохраняет `User.registrationDepartmentId` одновременно с аккаунтом. Новый пользователь всегда имеет глобальную роль `STUDENT`. При Google-регистрации выбранное направление передаётся в анкету, где сервер сохраняет его после входа. Пользователь может выбрать департамент один раз; запрос с другим ID после сохранения отклоняется. Поля роли и школы в регистрации запрещены строгой схемой.

Сохранён прежний порядок вступления: профиль → заявка → решение руководства → активное членство `MEMBER`. До одобрения доступны собственный профиль и заявка, командные данные закрыты. Выбор направления сам по себе не даёт руководящих прав.

Каждый запрос API проверяет актуальную роль и членство в БД; отозванное или приостановленное членство перестаёт действовать даже в существующей сессии. Подмена ID задачи, отчёта, канала или департамента не даёт доступ. Министр и вице-министр управляют обычными участниками и заявками, проверяют чужие отчёты и ведут работу своего департамента. Назначать руководство департамента и общие роли может администратор школы. Самопроверка отчётов запрещена.

Существующие общие роли администратора и руководства совета сохраняют прежние полномочия надзора. Обычный министр или вице-министр имеет доступ только через активное членство своего департамента. Общий школьный публичный календарь и сведения о руководстве остаются публичными, как и раньше.

## Email министров и вице-министров

1. Скопируйте `config/department-leadership.example.json` в `.local/department-leadership.json`.
2. Внесите email в `ministers` или `viceMinisters` нужного slug, например:

```json
{
  "sport": {
    "ministers": ["minister@example.org"],
    "viceMinisters": ["vice@example.org"]
  }
}
```

3. Аккаунты должны существовать, выбрать соответствующий департамент и войти через подтверждённый Google-аккаунт. Для парольного аккаунта можно подключить Google в профиле. Одного введённого при регистрации email недостаточно: владение почтой при парольной регистрации не подтверждается.
4. Оператор выполняет команды в доверенном окружении с правильными `DATABASE_URL` и `COUNCIL_SCHOOL_ID`:

```bash
npm run leadership:sync
npm run leadership:sync -- --apply
```

Первая команда показывает план без изменения прав. Вторая атомарно применяет весь план, создаёт активные членства руководителей и пишет аудит. Неподтверждённый аккаунт, конфликт департаментов, неизвестное направление или повторный email прерывают весь план. Повторное применение не дублирует аудит. Глобальная роль пользователя не меняется. Наличие email в файле никогда не обрабатывается при регистрации или входе.

`LEADERSHIP_CONFIG_PATH` позволяет указать другой приватный файл. `.local/` исключён из Git; не храните реальные списки в публичном примере, клиентском коде или `NEXT_PUBLIC_*` переменных. Удаление email из файла не отзывает уже выданные права: отзовите их в настройках администратора.

Альтернатива без файла: **Рабочее пространство → Настройки → Роли школы и назначение руководства**. Этот путь доступен существующему `SCHOOL_ADMIN` и позволяет вручную назначить роль в конкретном департаменте, в том числе проверенному оператором парольному аккаунту. Для первой установки без администратора сохраняется `npm run admin:bootstrap -- owner@example.org` после Google-входа. Существующему администратору повторный bootstrap не нужен.

## Безопасная миграция и публикация

Миграция `prisma/migrations/20261109185055_department_workspaces/migration.sql`:

- добавляет nullable-привязку регистрации и составной внешний ключ, запрещающий привязку к департаменту другой школы;
- добавляет отсутствующие департаменты и каналы `General` / `Announcements`;
- сохраняет существующие ID, названия, публичное имя министра, ставки, роли, статусы и всю историю;
- связывает исторический аккаунт с существующим активным членством, а аккаунты без членства — с Intellectual Development; это не создаёт для них членство и не обходит одобрение заявки;
- включает RLS на таблицах приложения и отзывает прямые права `PUBLIC`, `anon`, `authenticated`. Для NextAuth нет клиентских RLS-политик: браузер работает только через проверенный серверный API. Prisma использует доверенное серверное подключение. Не публикуйте строку подключения или service-role ключ в браузере.

Перед публикацией сохраните резервную копию рабочей БД и убедитесь, что `COUNCIL_SCHOOL_ID` соответствует существующей школе. Затем:

```bash
npm ci
npm run db:generate
npm run db:migrate
npm run db:seed
npm run build
```

Не используйте reset или пересоздание рабочей базы. `build` больше не запускает миграции с игнорированием ошибок: миграция — отдельный обязательный шаг до публикации новой версии. Парольные хеши и Google-аккаунты не изменяются, повторный вход не требуется для чтения актуальных прав. Автоматическая выдача глобальных прав по совпадению email удалена; уже сохранённые глобальные роли сохраняются.

Для автоматической публикации из GitHub добавлен `vercel.json`: Vercel выполняет миграции, генерацию Prisma, назначение утверждённых министров и сборку. Ошибка или недоступность базы прерывает сборку до публикации. Обычная локальная команда `npm run build` по-прежнему не изменяет базу. Для preview задавайте отдельную тестовую базу в переменных окружения Vercel.

Для нового адреса хешируйте `email.trim().toLowerCase()` алгоритмом SHA-256 и укажите результат у slug департамента. Отпечатки служат идентификаторами, не секретами и не доказательством владения почтой.

`npm run leadership:approved` показывает план, `npm run leadership:approved -- --apply` применяет его. Деплой запускает применение к уже существующим аккаунтам с подтверждённым входом Google. Если аккаунта ещё нет, назначение выполняется после успешного Google OAuth в событии `signIn`. Регистрация с паролем и выбранным департаментом не активирует роль. Для адреса mail.ru/iCloud нужен Google-аккаунт, зарегистрированный с этим адресом, либо ручное назначение администратором после проверки владельца.

Выдаётся только `MINISTER` указанного департамента в основной школе. Настроенное владельцем назначение закрепляет этот департамент в профиле, сохраняет прежние записи и членства и не меняет глобальные роли. Назначение отмечается в аудите однократно: последующие отзыв, блокировка или понижение роли администратором сохраняются при новых входах и деплоях. Пользователям с парольным аккаунтом Google не подключается автоматически.

## Проверки

```bash
npm run typecheck
npm run lint
npm run test:prepare
npm test
npx tsx scripts/verify-department-migration.ts
npm run build
```

Для тестов требуется отдельная локальная `TEST_DATABASE_URL` с именем, заканчивающимся на `_test`. Основной набор очищает только эту выделенную базу. Проверка миграции создаёт отдельную временную базу, применяет прежние миграции и исторические записи, затем новую миграцию и сравнивает историю до/после.

Полная HTTP-проверка работает отдельно от основной тестовой БД:

```powershell
$env:TEST_DATABASE_URL='postgresql://council:council@127.0.0.1:5432/council_ui_test'
npm run test:prepare
$env:DATABASE_URL=$env:TEST_DATABASE_URL
npm run db:seed
npm run build
npx tsx scripts/serve-verification.ts
# В другом терминале с тем же DATABASE_URL:
npx tsx scripts/verify-departments-http.ts
```

QA-сервер привязан только к localhost и к явно заданной локальной базе `*_test`, использует случайный временный секрет и не подключает боевой Google OAuth. HTTP-сценарии создают синтетические аккаунты и выполняют настоящий парольный вход через NextAuth, регистрацию во всех семи департаментах, одобрение заявки, создание задач, подачу отчётов, подтверждение вице-министром, отклонение министром, проверку лидерборда, запрет доступа к чужим ID и повышения роли. Google OAuth проверяется интеграционными тестами обработки подтверждённой идентичности; интерактивный вход реальным Google-аккаунтом требует работающего OAuth окружения.

Результаты проверки 10 ноября 2026: 44 интеграционных теста прошли; HTTP-сценарии семи департаментов и воспроизведение миграции прошли; ESLint, TypeScript и production-сборка прошли. Форма регистрации и кабинет проверены на компьютере и телефоне; устранено горизонтальное переполнение формы. Дополнительно проверяется закрытие данных через непривилегированную SQL-роль даже при выданном SELECT.

Назначение утверждённых министров дополнительно проверено семью интеграционными тестами на PostgreSQL: всего 51 тест прошёл. Проверены защита от парольной регистрации с чужой почтой, изоляция департаментов, идемпотентность, сохранение блокировок/отзыва/понижения роли и истории. ESLint и production-сборка прошли.

Прямой доступ к рабочей БД через подключённый Supabase недоступен. Публикация выполняется через GitHub и существующую интеграцию Vercel; результат проверяется по статусу деплоя. Индивидуальные назначения без прямого чтения рабочей БД не подтверждаются отдельно.
