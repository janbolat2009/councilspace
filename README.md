# councilspace

**Council Space** — веб-платформа школьного **Student Council** с основным акцентом на **Intellectual Development Department** (министр — **Zhanbolat**).

Платформа объединяет публичное представительство студенческого совета и закрытое рабочее пространство команды: подачу и модерацию заявок на вступление, задачи со списками и канбаном, мероприятия и календарь с часовым поясом школы, отчёты о выполненной работе с проверкой руководителями, прозрачный журнал начислений часов и баллов, лидерборды по периодам, сохраняемый командный чат, уведомления и журнал административных действий.

---

## 1. Стек технологий

- **Framework:** Next.js 16 (App Router, TypeScript, Standalone output)
- **Стили и UI:** Tailwind CSS 4, доступные диалоги и примитивы (`@radix-ui/react-dialog`, `@radix-ui/react-slot`, `class-variance-authority`), иконки `lucide-react`, анимации `motion` с поддержкой `prefers-reduced-motion`
- **База данных:** PostgreSQL + Prisma 7 (`@prisma/client`, `@prisma/adapter-pg`, SQL-миграции и строгие `CHECK` / `UNIQUE` ограничения)
- **Авторизация:** NextAuth (`next-auth`, `@next-auth/prisma-adapter`) с Google OAuth и регистрацией по email/паролю; пароли хранятся как salted scrypt hash
- **Валидация и часовые пояса:** Zod 4, `date-fns`, `date-fns-tz` (хранение в UTC, отображение в часовом поясе школы, по умолчанию `Asia/Qyzylorda`)
- **Тестирование:** Vitest (интеграционные тесты поверх выделенной тестовой базы PostgreSQL)

## 2. Быстрый старт (локальная разработка)

Сначала установите зависимости командой `npm ci`, скопируйте `.env.example` в `.env` и задайте случайный `NEXTAUTH_SECRET`. Выберите один из двух вариантов PostgreSQL ниже. Не запускайте оба на одном порту. В Windows PowerShell для копирования используйте `Copy-Item .env.example .env`; существующий `.env` с ключами не перезаписывайте.

### Вариант А — PostgreSQL через Docker Compose

```bash
docker compose up -d
```

Контейнер `postgres:17-alpine` поднимется на `127.0.0.1:5432` с базой `council` (пользователь `council`, пароль `council`).

### Вариант Б — Встроенный локальный PostgreSQL (если Docker не установлен)

```bash
npm run db:local
```

Оставьте процесс запущенным в отдельном терминале — он инициализирует и запускает локальный экземпляр PostgreSQL на `127.0.0.1:5432` с хранением данных в `.local/postgres`.

### Установка зависимостей, миграции и запуск

1. Скопируйте файл переменных окружения:

```bash
cp .env.example .env
```

2. Сгенерируйте Prisma Client, примените миграции и создайте базовую запись школы и департамента **Intellectual Development** (министр — **Zhanbolat**, без фиктивных людей и ролей):

```bash
npm run db:generate
npm run db:migrate
npm run db:seed
```

3. Запустите сервер разработки:

```bash
npm run dev
```

Приложение откроется по адресу `http://localhost:3000`.

Открывайте именно `localhost:3000`, совпадающий с `NEXTAUTH_URL`. Адрес `127.0.0.1:3000` — другой origin и имеет отдельные cookies.

## 3. Демонстрационный режим (отдельный идемпотентный seed)

Демонстрационные данные **никогда** не загружаются автоматически в рабочую школу и требуют явного флага `ENABLE_DEMO=true`:

```bash
ENABLE_DEMO=true npm run db:demo
```

Что делает `db:demo`:
- создаёт изолированную демо-школу `demo-school` и департамент `Intellectual Development`;
- создаёт явно помеченные демонстрационные профили (`isDemo: true`, `@demo.invalid`);
- добавляет задачи разных статусов (`TODO`, `IN_PROGRESS`, `SUBMITTED`, `COMPLETED`);
- добавляет 5 мероприятий: **Интеллектуальная игра «Что? Где? Когда?»**, **Science Fair**, **Встреча с выпускниками**, **Математический футбол**, **Кейс-чемпионат** (без фиктивных подтверждённых гостей);
- добавляет отчёты с решениями (`APPROVED`, `PENDING`, `CHANGES_REQUESTED`, `REJECTED`) и сообщения в чате.

При `ENABLE_DEMO=true` на главной странице и по адресу `/demo` доступен безопасный обзор демо-пространства, а при `ENABLE_DEV_LOGIN=true` (работает **только** в `NODE_ENV=development` и только на `localhost` / `127.0.0.1`) на странице `/login` можно переключаться между демо-ролями для локальной проверки интерфейса.

## 4. Настройка Google OAuth

На `/login` доступны Google и email/пароль; на `/register` создаётся обычный аккаунт ученика без прав команды. После успешного входа `/auth/complete` отправляет нового пользователя на `/onboarding`, существующего — в `/workspace`. Профиль и заявка сохраняются в PostgreSQL.

Если email уже зарегистрирован с паролем, сначала войдите с паролем и нажмите «Подключить мой Google-аккаунт» в профиле. Автоматического объединения парольных аккаунтов по совпадению email нет. В профиле можно добавить пароль к Google-аккаунту или изменить существующий, указав текущий пароль. Вход и регистрация ограничены по частоте на сервере.

Подтверждение email письмом и восстановление забытого пароля по почте пока не реализованы. Парольная регистрация не подтверждает владение почтовым адресом; доступ в департамент всё равно требует отдельного одобрения.

1. Откройте [Google Cloud Console](https://console.cloud.google.com/) → **APIs & Services** → **OAuth consent screen** и настройте экран согласия.
2. Перейдите в **Credentials** → **Create Credentials** → **OAuth client ID** → тип **Web application**.
3. Укажите **Authorized JavaScript origins**:
   - Для локальной разработки: `http://localhost:3000`
   - Для production: `https://ваш-домен.школы`
4. Укажите точные **Authorized redirect URIs (Callback URLs)**:
   - Для локальной разработки:
     ```text
     http://localhost:3000/api/auth/callback/google
     ```
   - Для production:
     ```text
     https://ваш-домен.школы/api/auth/callback/google
     ```
5. Скопируйте выданные ключи в `.env`:
   ```env
   GOOGLE_CLIENT_ID=ваш_client_id.apps.googleusercontent.com
   GOOGLE_CLIENT_SECRET=ваш_client_secret
   # Необязательно: ограничить вход доменом школы (например, nis.edu.kz)
   GOOGLE_ALLOWED_DOMAIN=
   ```

## 5. Назначение первого School Admin и министра Zhanbolat

В целях безопасности первый случайный зарегистрированный пользователь **не становится** администратором, а профиль министра **Zhanbolat** не привязывается к аккаунту просто по совпадению имени.

1. Войдите на платформу через свой реальный Google-аккаунт на странице `/login`.
2. На сервере выполните команду bootstrap с email вашего Google-аккаунта:

```bash
npm run admin:bootstrap -- ваш-email@gmail.com
```

Что проверяет `admin:bootstrap`:
- выполняет транзакцию с `Serializable` изоляцией и PostgreSQL advisory lock (`pg_advisory_xact_lock`);
- убеждается, что в школе ещё нет ни одного `SCHOOL_ADMIN` (повторный запуск запрещён);
- проверяет, что пользователь вошёл через верифицированный провайдер `google` и не является демо-профилем;
- назначает глобальную роль `SCHOOL_ADMIN` и записывает событие `ADMIN_BOOTSTRAPPED` в `AuditLog`.

3. После получения прав `SCHOOL_ADMIN` откройте **Рабочее пространство → Настройки → Роли школы и назначение руководства**:
   - назначьте аккаунту Zhanbolat роль **Министр (`MINISTER`)** в департаменте **Intellectual Development**;
   - при необходимости назначьте `PRESIDENT`, `VICE_PRESIDENT`, `VICE_MINISTER` и создайте дополнительные департаменты через кнопку **«Добавить»**.

## 6. Инструкции для Production

1. Подготовьте серверную базу данных PostgreSQL 15+ и задайте переменные окружения:
   ```env
   DATABASE_URL=postgresql://user:password@db-host:5432/council?schema=public
   NEXTAUTH_URL=https://ваш-домен.школы
   NEXTAUTH_SECRET=случайная_строка_не_менее_32_байт
   GOOGLE_CLIENT_ID=...
   GOOGLE_CLIENT_SECRET=...
   COUNCIL_SCHOOL_ID=school
   ENABLE_DEMO=false
   ENABLE_DEV_LOGIN=false
   ```
2. Примените миграции и создайте базовую структуру школы и департамента Intellectual Development:
   ```bash
   npm ci
   npm run db:migrate
   npm run db:seed
   ```
3. Соберите и запустите production-приложение:
   ```bash
   npm run build
   npm start
   ```
4. Выполните `npm run admin:bootstrap -- ваш-email@домен` после первого входа через Google.

## 7. Проверка работоспособности и выполненные тесты

Для запуска полного набора проверок:

```bash
npm run typecheck
npm run lint
npm run test:prepare
npm test
npm run build
```

Для тестов задайте отдельный `TEST_DATABASE_URL`, например `postgresql://council:council@127.0.0.1:5432/council_test`. В PowerShell: `$env:TEST_DATABASE_URL='postgresql://council:council@127.0.0.1:5432/council_test'`. Тесты очищают только эту выделенную базу; имя должно заканчиваться на `_test`.

На 21.10.2026 успешно прошли 29 интеграционных тестов: 18 сценариев работы команды и 11 сценариев регистрации, хеширования, входа, связки Google и ограничений частоты. Также прошли TypeScript, ESLint без предупреждений и production-сборка. Подробности ручной проверки: [docs/verification.md](docs/verification.md).

Автоматическими интеграционными тестами (`tests/workflows.test.ts` на реальной PostgreSQL базе `council_test`) проверены все ключевые сценарии:
1. Подача заявки учеником, запрет повторной активной заявки, одобрение руководством и открытие доступа к рабочему пространству со статусом `MEMBER`.
2. Отклонённый и отозвавший заявку кандидат не получает доступ к закрытым данным и чату.
3. Создание задачи участником и отправка отчёта на 90 минут.
4. До подтверждения отчёта часы и баллы в `LedgerEntry` равны `0`.
5. После подтверждения при ставке `10 баллов/час` начисляются ровно `90 минут` (`1,5 ч`) и `15 баллов`.
6. Повторное и конкурентное параллельное подтверждение двумя руководителями не создаёт дублирующих начислений (транзакция `Serializable` + уникальное ограничение `@@unique([reportId, revision, kind])`).
7. Запрет подтверждения собственного отчёта (включая отчёты министров и администраторов).
8. Возврат отчёта на доработку (`CHANGES_REQUESTED`), исправление автором, повторная отправка и защита уже подтверждённого отчёта от незаметного редактирования.
9. Изменение ставки баллов департамента увеличивает `ruleVersion` и применяется только к новым подтверждениям, сохраняя исторические расчёты.
10. Отмена подтверждения (`REVERSE`) создаёт обратную запись `REVERSAL` с причиной и корректно пересчитывает часы, баллы и счётчик отчётов.
11. Корректировка подтверждённых минут проверяющим требует обязательного объяснения; заявленное и подтверждённое время хранятся раздельно.
12. Контроль суточного лимита (по умолчанию 12 часов / 720 минут) по сумме отчётов за день и поддержка документированного исключения (`overrideReason`).
13. Полная изоляция между департаментами: участник или министр другого департамента не может читать чужой чат, задачи, отчёты или отвечать на чужие сообщения прямым API-запросом.
14. Приостановка (`SUSPENDED`) и отзыв членства (`REVOKED`) немедленно закрывают доступ к чату и данным при сохранении истории работы.
15. Чат в PostgreSQL: пагинация по `sequence`, инкрементальная подгрузка новых сообщений и изменений/удалений, учёт непрочитанных, права канала `Announcements`, лимит частоты отправки и запись модераторских удалений в `AuditLog`.
16. Разграничение точных дедлайнов со временем (`dueAt` в UTC с конвертацией в `Asia/Qyzylorda`) и дедлайнов только по дате (`dueDate`).
17. Фильтрация лидерборда по дате фактического выполнения работы (`performedOn`), настраиваемые границы четвертей и учебного года без пересечений.

## 8. Список оставшихся внешних настроек

Для запуска в боевом режиме владельцу платформы необходимо:
1. Настроить OAuth Client для итогового домена и завершить контрольный вход своим Google-аккаунтом. Наличие локальных ключей само по себе не подтверждает полный OAuth-сценарий.
2. Указать боевой `DATABASE_URL`, `NEXTAUTH_URL` и сгенерировать криптостойкий `NEXTAUTH_SECRET` (`openssl rand -base64 32`).
3. После первого входа через Google выполнить `npm run admin:bootstrap -- <email>` и назначить роль `MINISTER` для аккаунта Zhanbolat в интерфейсе администратора.
